# آزمایشگاه DNSTT + StormDNS — مرحلهٔ اول

**وضعیت: نمونهٔ آزمایشی اجراشده، نه ادغام آماده در اپ اندروید.** این پوشه برای اثبات مسیر اتصال، بررسی سازگاری و آزمون استفادهٔ مستقیم از balancer واقعی StormDNS ساخته شده است. هیچ تغییری در پروتکل سرور یا پیاده‌سازی balancer اصلی نداده‌ایم.

## یافتهٔ اصلی

فایل AM-MST سرورهای BD NET را چنین توصیف می‌کند: یک کلاینت DNSTT اختصاصی یک اتصال TCP محلی باز می‌کند؛ سمت دیگر این تونل یک **SOCKS5 با احراز هویت** است. این با SSH-over-DNS یکی نیست. برای یک سرور SSH واقعی باید مشخصات و روش احراز هویت SSH جداگانه دریافت شود. MasterDNS/StormDNS نمی‌توانند فریم‌های اختصاصی خود را مستقیماً به این سرور بفرستند؛ در این آزمایش فقط انتخاب مسیر DNS به balancer اصلی StormDNS سپرده شده است.

مسیر آزمایش‌شده:

```text
کلاینت سازگار DNSTT
   → UDP روی loopback
   → گیت‌وی آزمایشی DNS (انتخاب مسیر با stormdns-go/internal/client.Balancer)
   → DNS resolver A یا B
   → سرور DNSTT
   → SOCKS5 همراه احراز هویت
   → HTTPS
```

گیت‌وی بستهٔ DNS تونل را تغییر نمی‌دهد؛ شناسه و سؤالِ پاسخ را بررسی می‌کند و پاسخ معتبر را به کلاینت برمی‌گرداند. نام مقصد به zone مشخص محدود است، فقط روی loopback گوش می‌کند، concurrency محدود دارد و پس از timeout یک resolver دیگر را امتحان می‌کند. معیار فعلی **round-robin** است؛ این نمونه هنوز اسکنر، MTU discovery، تنظیم خودکار یا تمام قابلیت‌های Master/Storm را ندارد.

## نتیجهٔ تست‌ها — ۲۹ اکتبر ۲۰۲۶

در محیط Linux و qemu-arm64، روی `sd-de1.liftmeon.org` با مجوز استفاده‌ای که کاربر تأیید کرده و باینری سازگار عرضه‌شده در مخزن AM-MST:

| مسیر | نتیجه |
|---|---|
| کلاینت سازگار ← سرور مستقیم | SOCKS auth و CONNECT موفق؛ HTTPS با گواهی معتبر و HTTP 200 |
| کلاینت ← گیت‌وی Storm ← سرور مستقیم | موفق، HTTP 200 |
| کلاینت ← گیت‌وی Storm ← 1.1.1.1 و 8.8.8.8 | موفق، HTTP 200؛ هر دو resolver پاسخ دادند |

در اجرای ثبت‌شده روی `de1`، شمار پاسخ‌های معتبر DNS در تست دو resolver به‌ترتیب ۴۵ و ۳۷ بود. این شمارنده **تعداد پاسخ DNS** است نه تعداد اتصال یا اندازهٔ ترافیک. زمان‌های تست سرعت‌سنجی معتبر محسوب نمی‌شوند. [نتیجهٔ de1](live-test-result.json)

سرور `de20` نیز جداگانه آزمایش شد: اتصال مستقیم و از طریق گیت‌وی موفق بود؛ نخستین اجرای تست دو resolver در مرحلهٔ پاسخ HTTPS شکست خورد. در اجرای مجدد، هر سه حالت موفق بودند و دو resolver به‌ترتیب ۵۰ و ۴۳ پاسخ معتبر دادند. علت دقیق شکست نخست مشخص نشده و نباید به عنوان اثبات پایداری برداشت شود. [اجرای نخست](live-test-de20-result.json) · [اجرای مجدد](live-test-de20-retest-result.json)

تست انتهابه‌انتهای دیگر با **سرور استاندارد dnstt محلی** و دو resolver شبیه‌سازی‌شده، HTTP 200 و استفاده از هر دو مسیر را نشان داد. چهار تست واحد با `go test -race` هم برای توزیع round-robin، خروج از zone، failover بعد از timeout، شناسهٔ نادرست پاسخ و اجرا از loopback پاس شدند. [نتیجهٔ محلی](local-test-result.json)

این تست‌ها اثبات سازگاری با همهٔ ۲۰ سرور، عملکرد در ایران، پایداری بلندمدت، نبود نشت DNS یا کارکرد اندروید نیستند.

## فایل‌ها

- `main.go`: واسط آزمایشی DNS با استفادهٔ مستقیم از `internal/client.Balancer` سورس StormDNS که WhiteDNS پین کرده است؛ انتخاب fallback فقط در صورت شکست مسیر اول انجام می‌شود.
- `main_test.go`: تست‌های واحد و race detector.
- `test_e2e.py`: تست انتهابه‌انتهای محلی با dnstt استاندارد و HTTP محلی.
- `test_bdnet.py`: تست مجاز واقعی، شامل auth، SOCKS CONNECT و HTTPS با بررسی گواهی. اطلاعات ورود را از JSON محلی می‌خواند و چاپ نمی‌کند.
- `bdnet-candidates.json`: ۲۰ پروفایل **نامزد** استخراج‌شده از فایل معرفی‌شده؛ بدون اطلاعات ورود. این فایل هنوز به پروفایل‌های پیش‌فرض اپ وصل نشده و همهٔ سرورها آزمایش نشده‌اند.
- `live-test-result.json`، `live-test-de20-result.json`، `live-test-de20-retest-result.json` و `local-test-result.json`: داده‌های تست‌ها؛ هر دو نتیجهٔ de20 نگه داشته شده‌اند.

## اجرای مجدد

نیازمندی‌ها: Go 1.26.1، Python 3، سورس StormDNS در `../third_party/StormDNS`، و در تست زنده qemu-aarch64 و sysroot سازگار Android. به نسخهٔ دقیق StormDNS در WhiteDNS توجه کنید: `74385bc9854d4f4aab9cb7d78dc8c90de75860bd`.

```sh
cd dnstt-lab
go test -race -v ./...
go build -o /tmp/dnsbridge .
```

برای تست محلی می‌توانید کلاینت و سرور dnstt استاندارد را از سورس `Mygod/dnstt` کامیت `17aa1fed864cd5493e3d09a14df1b8b5cc1df123` بسازید و مسیر باینری‌ها را به اسکریپت بدهید:

```sh
python3 test_e2e.py --client /path/to/dnstt-client \
  --server /path/to/dnstt-server --bridge /tmp/dnsbridge
```

تست زنده تنها با اجازهٔ اپراتور و باینری سازگارِ مجاز:

```sh
python3 test_bdnet.py --config /path/to/slowdns.json \
  --client /path/to/libxdnstt.so --bridge /tmp/dnsbridge \
  --qemu /usr/bin/qemu-aarch64-static --sysroot /path/to/android-arm64-sysroot
```

باینری اختصاصی BD NET یا فایل اطلاعات ورود در این پوشه توزیع نمی‌شود. برچسب `prince` را نباید با کلید عمومی استاندارد ۶۴رقمی dnstt اشتباه گرفت: کلاینت عمومی را با فرض سازگاری آن نمی‌توان جایگزین باینری اختصاصی کرد. هش باینری استفاده‌شده برای تست: `9fb149ad83ab5f94e32c298ecc0bbc9840159ea6365413566b74f61aa7c66a86`.

## کارهای باقی‌مانده پیش از اضافه‌شدن به WhiteDNS

1. روشن‌شدن دسترسی و مجوز سورس/باینری کلاینت سازگار و ساخت آن برای ABIهای پشتیبانی‌شده؛ `-pubkey prince` در کلاینت استاندارد کافی نیست.
2. اتصال چرخهٔ عمر گیت‌وی و کلاینت به `VpnService` و SOCKS محلی، محافظت سوکت‌ها در برابر VPN loop، و طراحی ذخیره‌سازی امن اطلاعات ورود.
3. ادغام واقعی پروفایل‌ها، و تست‌های UI و ساخت اندروید؛ قبل از نمایش Connected باید auth، CONNECT و انتقال واقعی داده اثبات شود.
4. اتصال اسکنر و آمار اصیل Storm/Cotten با probe سازگار DNSTT؛ یک پاسخ DNS معمولی به معنی قابلیت عبور تونل نیست.
5. در صورت نیاز به چند سرور مستقل، توزیع **اتصال‌های جداگانه** بین چند تونل و failover؛ ترکیب بسته‌های یک سشن واحد بین سرورهای مستقل بدون پشتیبانی سمت سرور ایمن یا تضمین‌شده نیست.
6. تست روی دستگاه و شبکهٔ واقعی، تغییر شبکه، شکست resolver، قطع پردازش، چندین اتصال هم‌زمان، و بررسی نشت DNS/IPv6.

یادآوری مجوز: خود WhiteDNS source-available و اختصاصی است و README آن ساخت محلی برای بررسی/مشارکت در پروژهٔ رسمی را مجاز می‌داند؛ انتشار APK تغییر‌یافته یا بازتوزیع نیازمند مجوز است. مجوز باینری‌های شخص ثالث نیز جداگانه باید بررسی شود.
